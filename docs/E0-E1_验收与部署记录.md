## 内容复核

独立从原始规格的明确行范围逐字比对 6 demand、3 linked、3 ordinary、6 tips，共 18 段主正文，均一致。仅移除 Markdown 引用符及格式换行空格；未将“假设用户回应”预填为用户历史。

发现并修复了 W1-G “不设置”下负例被作为系统词条导入的问题。修复后为 53 个合法系统引用块，正文一致。三组 linked／ordinary 共享场景元数据，季节与时段分开；linked 在本阶段仅导入内容，未实现历史联动。

## 可靠性审查

以下问题已修复，并以源码复核和针对性回归核实：

1. 初次读取的服务故障被误当成未登录：区分 401 与服务不可用。
2. 已落库但响应丢失后修改文字，再试会假报成功：仅对不确定传输故障查询结果，并核验同来信和正文摘要。
3. 一次性邀请响应丢失无法恢复：Admin 为同一参与者重发邀请、撤销旧会话，保留历史。
4. Admin 重试可能多投递下一张卡：服务端保存幂等操作结果；界面“写入成功、刷新失败”的重试继续使用同一请求键，端到端回归通过。
5. 本机启动脚本验证健康检查后才报告启动成功，重复启动保留有效进程信息。

最终检查：执行者的 `npm run build`、`npm run test:e2e`（2/2）及应用＋PostgreSQL 实际重启恢复通过，统筹读取了对应日志。代码冻结后，统筹另行实跑 `npm run content:check`、`npm run typecheck` 和 `npm test`（3/3）通过；其中真实数据库测试包括 T1/T2/T3/T7、8 次并发发送和参与者隔离。内容检查的首次运行受本机沙盒 IPC 限制，获准后用同一命令成功执行，未把环境错误计为业务测试失败或跳过。

## 部署边界

现有 GitHub Pages 仅托管静态策划页面；本应用需要 Node 运行环境和独立 PostgreSQL。只读盘点没有找到可确认属于本项目的已有云站点及数据库，未复用其他项目资源。

当前保留通用 Node 部署方式和 Dockerfile。平台选择、数据库连接与服务器端环境变量落实后，执行迁移、发布及线上写入／读取验证。Dockerfile 本轮本机未运行 Docker 构建。不得将构建产物、CI 通过或静态站点部署等同于全栈应用已可在线使用。

本轮不包含 E2 的 linked 投递、来源更正删除、暂停恢复、自留句和 REALTIME worker。输入检查为明确标注的内部合成适配器，未验证真实风险识别能力。
